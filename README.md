# Axd_Line_Switch (告警触发线路自动切换系统)

当 AIOps 平台产生告警时，根据告警标题自动匹配站点与线路方向，登录对应网络设备并按序下发预维护的切换命令，实现线路自动切换。**Python 标准库单文件实现，零第三方依赖**，适合内网生产环境直接部署。

---

## 工作流程

```
AIOps 告警 ──POST /api/alert {"title":"站点A-4G专线中断"}──▶ 本系统
                                                            │
                                            1. 按标题匹配"切换动作"
                                               (包含关键词 / 正则)
                                                            │
                                            2. 找到动作绑定的设备
                                               (站点 + telnet/ssh)
                                                            │
                                            3. 后台队列登录设备，逐条下发
                                               命令块(每条等提示符回归)
                                                            │
                                            4. 执行记录落库，Web 查看回显
```

- 命令块完全由 Web 端维护（如华为/H3C BGP AS-PATH 调整三方向命令），`#` 开头行为注释自动跳过；
- `quit/exit/logout` 类断开命令发送后不等待提示符；
- 同一动作有**冷却时间**（默认全局 300 秒）防止重复告警反复切换；**演练（dry-run）不受冷却限制**，只登录验证不下发命令；
- 所有执行任务**单线程串行**（切换操作不应并发）；同一告警标题命中多个动作时只执行第一个（按动作 ID 序）。

## 快速开始

```bash
cp .env.example .env && vi .env   # 修改 LS_SECRET 为随机串（用于设备密码加密）
chmod 600 .env
./start.sh start                  # 后台守护: 日志 lineswitch.log, pid lineswitch.pid
./start.sh status|stop|restart    # 其它命令；不带参数=前台运行
```

访问 `http://<服务器IP>:8090`，默认登录密码 `admin123`（登录后请在"全局设置"修改）。

## 配置告警回调

AIOps 告警动作中配置 HTTP 回调：

```
POST http://<本机IP>:8090/api/alert
Header:  X-API-Token: <在"全局设置"中查看>
Body:    {"title": "告警标题"}       # 兼容 alarm_title / name 字段；支持 dry_run:true 演练
```

响应示例：

```json
{"matched": true, "task_id": 5, "executed": true, "action": {"id": 1, "name": "切到4G"}}
{"matched": true, "task_id": null, "executed": false, "skip_reason": "冷却期内（300s）"}
{"matched": false, "title": "..."}
```

## 如何确认「告警标题 ↔ 站点/线路」对应关系

告警标题匹配是**人工维护的关键词规则**，系统提供两级校验工具（「切换动作」页顶部"匹配预检"卡片）：

1. **单条标题测试**：粘贴一条真实告警标题，立即显示命中哪个动作、命中依据（哪几个关键词）、将执行多少条命令；
2. **真实告警回放**：配置 AIOps 地址与 Token 后，拉取近 1/7/14/30 天真实告警标题批量回放，输出「命中统计 / 未命中标题清单（按次数排序）」，用于判断：
   - 该动作的命中条数是否与该线路真实告警频率吻合（=0 说明关键词写错了）；
   - 未命中清单里是否有**本应触发切换**的标题（有 → 补关键词变体）。

### 关键实践（基于真实告警数据分析）

AIOps 标题常见形态（同一线路可能存在多种写法，务必覆盖）：

```
【ICMP中断】41.243.21.170-华刚卢本-Airtel            ← IP-站点-线路（最常见）
【ICMP丢包】中铁绿纱矿业-刚果金-DIA-41.243.9.14        ← 站点-区域-线路-IP（IP 在后）
【ICMP丢包】科米卡-约堡-刚果金Airtel专线              ← 站点-中继-线路，无独立 IP
【ICMP丢包】中海油米桑专线                            ← 仅站点名，无线路标识
【网络设备】接口错包 ICTMGL-ASW-011                   ← 设备名，空格分隔
```

- **首选 "IP + 线路运营商" 双关键词**（如 `41.243.21.170,Airtel`）：包含匹配**与顺序无关**，因此 IP 在前/在后都能命中；IP 也不会因中文名空格（`41.243.21.182- 鹏欣SMCO`）、括号别名（`华友1（HUAYOU LOCAL）`）而失效。
- **不要只用中文站点名**：同一区域存在近似名（华友1/华友2、华刚卢本/华刚科卢），且常混排中英文别名。
- **同一站点多条线路必须带线路标识**：只用站点名无法区分 Airtel / Vodacom / 4G，会在错误方向执行切换。
- **未命中不等于配置错误**：ESXi / AP 掉线 / 连接数使用率 / 接口错包等告警本身不需要切换线路，应保留为未命中。
- 匹配是**包含式**（全部关键词都出现才命中），关键词过短易误命中（如单写 `4G`），建议始终带上站点或 IP 作为锚点。

## 多条线路的切换顺序怎么配

系统的"顺序"分三层，前两层内建，第三层刻意不做（用命令块的幂等性代替）：

| 层 | 谁决定顺序 | 现状 |
|---|---|---|
| 命令块内部 | 命令块**从上到下**的行序，每条命令等设备提示符回归后才发下一条 | 内建，`#` 行注释自动跳过 |
| 一次告警命中多个动作 | 按动作 ID 序**只执行第一个**，其余仅计数不执行（切换动作互斥，不能并发） | 内建 |
| 多步骤/跨设备编排、线路自动级联降级 | —— | 不提供。用"一个方向一个动作 + 命令块自带完整状态"替代 |

### 推荐配置：一个方向一个动作（命令块对称）

同一站点 N 条线路 → 建 N 个动作，动作名 = 目标状态，每个命令块都是**完整状态迁移**：

| 动作 | 匹配关键词（IP + 线路） | 命令块要点 |
|---|---|---|
| 站点A-切到 Airtel | `41.243.21.170,Airtel` | undo Vodacom → undo 4G → undo Airtel → peer Airtel 挂 im |
| 站点A-切到 Vodacom | `41.243.21.170,Vodacom` | undo Airtel → undo 4G → undo Vodacom → peer Vodacom 挂 im |
| 站点A-切到 4G | `41.243.21.170,4G` | undo Airtel → undo Vodacom → undo 4G → peer 4G 挂 im |

三条硬规则：

1. **`undo` 必须包含"自己"那个方向**（先 undo 再 add），否则重复执行会残留上一次的策略；
2. **各方向命令块要互相对称**（每块都 undo 掉另外所有方向），这样任一动作都能从任意当前状态切到位，不需要知道"从哪切过来"；
3. **回切要么用"切回主线路"独立动作，要么填在动作的"回切命令块"里**（手动触发用）；不要指望告警恢复自动回切——那需要线路状态跟踪。

### 为什么不做"线路优先级自动降级"

自动降级要求系统维护"每条线路当前 up/down"和"当前生效线路"，而线路可用性的可靠来源只有 AIOps 恢复告警或主动探测；状态一旦过期就会基于错误前提切换。把"哪个方向该生效"显式交给告警标题匹配 + 人工可读的命令块，比隐式状态机更可控、更容易审计。

### 跨设备顺序（如先切核心路由再切出口设备）

当前一个动作只能绑一台设备。若必须跨设备，建议拆成两个动作分别匹配不同告警标题，或等后续加入"动作多步骤"能力；不要用两台设备同时抢同一告警。

## 当前线路查询与切换后验证

真实的切换不能"发完命令就算成功"。系统为每台设备/每个动作提供验证闭环：

### 设备侧（查询当前生效线路）

| 字段 | 说明 | 示例 |
|------|------|------|
| 状态查询命令 | 切换前/查线路时执行的命令 | `display ip routing-table` |
| 当前线路正则 | 可选；自定义提取标识（捕获组1） | 留空用默认解析 |
| 线路映射 | 每行 `下一跳IP=线路名` | `192.168.130.2=Vodacom` |

默认解析逻辑：在回显中找 `0.0.0.0/0` 路由行（排除 Direct/InLoop/127.x），取下一跳 IP，再经线路映射转为线路名。

- 设备列表有「查线路」按钮（`POST /api/devices/{id}/status`）；
- 每次执行切换前自动查询当前线路，记录在执行记录的「切换前当前线路」中；
- **演练（dry-run）也会查**，用于"只看当前在哪条线路、不实际切换"。

### 动作侧（切换后验证）

| 字段 | 说明 | 示例 |
|------|------|------|
| 验证命令块 | 切换命令下发后执行（独立会话重新登录） | `display ip routing-table` |
| 期望关键词 | 逗号分隔，须全部出现在验证回显中 | `192.168.130.22` |

执行状态语义：

| 状态 | 含义 |
|------|------|
| `success` | 切换命令下发成功 **且** 验证回显包含全部期望关键词（如 0.0.0.0 下一跳已是目标线路） |
| `verify_failed` | 命令已下发，但验证未通过（路由未收敛或切换失败）——**需人工介入** |
| `failed` | 登录失败 / 命令被设备拒绝 / 会话异常 |

验证为什么用独立会话：切换命令块常以 `quit` 结尾断开会话（命令块也可能中途改变视图状态），验证重新登录一次设备查路由表，结果不受前一会话状态影响，也避免 broken pipe。

### 配置示例（对应 BGP 三方向切换）

设备：`状态查询命令=display ip routing-table`，线路映射三行
`192.168.130.2=Vodacom` / `192.168.130.10=Airtel` / `192.168.130.22=4G`。

动作"切到4G"：验证命令块 `display ip routing-table`，期望关键词 `192.168.130.22`。
执行记录将显示：`切换前当前线路: Airtel → success（或 verify_failed）`。

## 执行日志与排障留痕

每条执行记录保存三层信息，全部可在「执行记录 → 点击行」查看：

| 层 | 内容 | 用途 |
|---|---|---|
| 命令级 `output` | 清理后的回显（去掉命令行 echo 与提示符），最多 8000 字符 | 日常查阅 |
| 命令级 `raw_output` | **原始回显全文**（含设备回显的命令行、提示符、错误信息），最多 20000 字符 | 判断设备真实反馈（如 `% Unrecognized command`、视图没切过去） |
| 会话级 `session_log` | **完整会话原文**：`[TX] 命令 / [RX] 回显` 逐步交替，含登录 banner、认证交互、init_command、验证会话全过程 | 排障核心：看清"到底发了什么、设备回了什么" |

补充说明：

- 密码在会话原文中自动替换为 `******`，不落库明文；
- **登录失败**（口令错、连接拒绝、提示符不匹配）同样保存登录阶段原文——这是最难查也最容易缺现场的情况；
- SSH 的 host key 提示等 stderr 输出一并记录（ssh 走 pty，stderr 与 stdout 合流）；
- `quit/exit` 等不等待提示符的命令，回显记为"该命令不等待回显，会话已断开"，不会误显示上一条命令的残留；
- 验证阶段使用**独立会话重新登录**，其收发也并入 `session_log`，标注 `[验证会话开始：重新登录设备]`。

## API 一览

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/alert` | 告警入口（X-API-Token 鉴权） |
| GET | `/api/task/{id}` | 查任务状态（供回调方轮询） |
| POST/PUT/DELETE | `/api/actions[/{id}]` | 切换动作 CRUD |
| POST/PUT/DELETE | `/api/devices[/{id}]` | 设备 CRUD（密码留空=不修改） |
| POST/PUT/DELETE | `/api/sites[/{id}]` | 站点 CRUD |
| POST | `/api/exec/{action_id}` | 手动执行，`?dry_run=1` 演练、`?rollback=1` 回切 |
| POST | `/api/devices/{id}/test` | 设备连通测试 |
| POST | `/api/match/test` | 单条告警标题匹配预检（返回命中动作与依据） |
| POST | `/api/match/replay` | 拉取近 N 天真实告警标题批量回放（`{"days":7}`） |
| GET | `/api/logs?limit=N`、`/api/logs/{id}` | 执行记录与详情 |

鉴权：Web 登录 Cookie 或 `X-API-Token` 请求头任一。

## 数据模型

```
sites(站点) ── devices(设备: host/protocol/账号/加密密码/init_command/提示符/超时)
            └─ actions(动作: 匹配方式+关键词、设备、command_block、rollback_block、冷却)
exec_logs / exec_steps  每次执行的日志与逐条命令回显
kv 全局设置(web_password / api_token / global_cooldown)
```

## 环境变量

| 变量 | 默认 | 说明 |

| `LS_PORT` | 8090 | 监听端口 |

## 安全说明

- 设备密码以 `LS_SECRET` 派生密钥 HMAC 流加密落库，不出现在日志与接口返回中；SSH 登录密码经 pty 写入，不进进程列表与命令行。
- 切换命令不做白名单限制（按设计命令完全自定义），建议：上线前先用"演练"验证登录连通，再用"执行"生效；生产 `LS_SECRET` 务必修改。
